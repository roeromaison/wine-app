# ワインテイスティング記録アプリ

香味13項目の評価を記録し、レーダーチャートと PCA（主成分分析）で自分の好みを見るための個人用アプリ。
これまで Excel + R でやっていた作業を、ブラウザ上で完結させることを目指している。

## 構成

| 層 | 技術 | 場所 |
| --- | --- | --- |
| フロントエンド | React 18 + Vite + Recharts | `frontend/` |
| バックエンド | FastAPI + SQLAlchemy | `backend/` |
| データベース | SQLite（`backend/wine.db`／個人版のみ） | 自動生成 |
| 分析 | scikit-learn | `backend/app/services/analysis.py` |

## 2つの動作モード

同じコードベースを環境変数で切り替える。

| | personal（既定） | public |
| --- | --- | --- |
| 用途 | 自分専用 | 一般公開デモ |
| 記録の保存先 | SQLite | 訪問者のブラウザ（localStorage） |
| 記録CRUD API | あり | **なし**（ルーター自体を読み込まない） |
| ファイル取り込み | 解析してDBに保存 | 解析して返すだけ |
| サーバーに残るデータ | あり | **なし** |

切り替えはバックエンドが `WINE_APP_MODE`、フロントが `VITE_APP_MODE`。

公開版で記録CRUDを閉じているのは、開けておくと「誰でも書き込める共有DB」に
なってしまい、訪問者同士の記録が混ざるうえ荒らしの標的にもなるため。

**分析APIは両モードとも同じもの**を使う。DBを読まず、送られてきた記録を計算して
返すだけの形（`POST /api/analysis/...`）にしてあるので、記録がどこにあっても動く。
これによりモードごとに分析コードを分ける必要がなくなっている。

デプロイ手順は [docs/DEPLOY.md](docs/DEPLOY.md)。

### 公開版の構成（画面とAPIを分ける理由）

画面は静的ホスティング（Render Static Site）、分析APIは Render Web Service に分けている。

Render の無料プランは15分アクセスがないと眠り、次の訪問者は起動を1分ほど待つ。
画面ごと Render に置くと**その1分は真っ白**になる。アプリのファイル自体が
まだ届いていないので、「読み込み中」と表示することすらできないためである。

画面を静的ホスティングに分けると画面は常に即表示され、待ちは分析の初回だけに
なる。そのときはアプリが動いているので「計算中…」を出せる。

この構成では画面とAPIが別オリジンになるため、
- フロントは `VITE_API_BASE`（`frontend/.env.production`）でAPIのURLを指定する
- バックエンドは `WINE_APP_ALLOWED_ORIGINS` で許可オリジンを指定する
  （未設定なら公開版は全許可。認証もCookieも保存データも無いAPIなので、
  CORSが本来守る「ログイン中の利用者になりすまされる」危険が成立しない）

## 起動方法

ターミナルを2つ開いて、それぞれで以下を実行する。

**1) バックエンド（ポート8000）**

```bash
cd backend && .venv/Scripts/uvicorn app.main:app --reload
```

**2) フロントエンド（ポート5173）**

```bash
cd frontend && npm run dev
```

ブラウザで http://localhost:5173 を開く。
API 仕様は http://127.0.0.1:8000/docs で確認できる。

## 初回セットアップ

すでに実行済みだが、別のPCで動かす場合は以下が必要。

```bash
cd backend && python -m venv .venv && .venv/Scripts/pip install -r requirements.txt
```

```bash
cd frontend && npm install
```

## 画面

- **記録する** — ワイン1本の情報と香味13項目を入力して保存。右側に入力中のレーダーチャートと記録一覧が並ぶ。一覧の記録をクリックするとその1本のレーダーに切り替わり、「編集」を押すと左のフォームに読み込まれて上書き保存できる。
- **おすすめ** — 高く評価した記録の香味から「好みプロファイル」を作り、同梱カタログ（maison の実記録80本）の中から香味の近い1本を提案する。診断タイプ名・X共有・購入リンクつき。記録3件から動く。詳しくは [docs/RECOMMEND.md](docs/RECOMMEND.md)。
- **分析（PCA）** — 色（赤/白/ロゼ/オレンジ）ごとに全記録を2次元にマッピングする。点が近いほど香味の傾向が似ている。品種・国・地域で色分けを切り替えられる。
- **クラスター** — 香味の似たワインをグループ分けし、同じ PCA マップをグループで色分けする。グループごとに香味13項目の平均プロファイル（棒の長さが平均値、右の数字が全体平均とのズレ）と所属ワインを表示する。
- **ヒートマップ** — 産地（国／地域）× 品種の平均総合スコア。色が濃いほど高評価。
- **インポート** — これまでの Excel / CSV をアップロードして一括登録する。

## インポートについて

- `.xlsx` / `.xlsm` / `.csv` / `.tsv` に対応。
- CSV の文字コードは UTF-8（BOM有無どちらも）と Shift-JIS を自動判別する。既存の `wine_log.csv` は Shift-JIS。
- 1行目を見出し行として扱い、`name` 列が必須。
- **ワイン名 + 日付**が同じ行を「同じ1本」とみなす。既にある記録の扱いは画面で選べる。
  - **重複は飛ばす**（既定）— 新しい行だけ追加する。同じファイルを二度取り込んでも二重登録にならない
  - **既存行を上書きする** — Excel 側で直した内容をアプリに反映する。中身が同じだった行は「変更なし」として数える
- タイプ（color）が判別できない行はスキップし、理由を画面に一覧表示する。

## PCA の計算方法

既存の R コード（`wine-notes/index_rev.qmd`）と同じ手順を Python で再現している。

1. 指定した color で絞り込む
2. 香味13項目がすべて埋まっている記録だけを使う
3. 分散が `var_threshold`（既定 0.15）未満の香味軸を除外する — 全部同じ点数を付けている軸は好みの違いを説明しないため
4. 平均0・標準偏差1に標準化してから主成分分析

R の `prcomp(scale. = TRUE)` は不偏標準偏差（n-1）で割るため、`StandardScaler`（母標準偏差）ではなく手計算で標準化している。ここを揃えないと既存の R の出力と座標のスケールがずれる。

主成分の符号は数学的にどちらでもよいので、「絶対値が最大の loading を正にする」というルールで固定してある。これがないと、記録を1件足すたびに図が上下左右に反転して見えてしまう。

## データ項目

`date, name, country, region, variety, color, style, blend_note, vintage, price_yen, purchase, abv, temp, decant_min`、
香味13項目（`fruit, floral, herb, spice, oak, vanilla, earth, mineral, acid, tannin, sweet, body, finish`、各0〜5）、
`overall_0_10, repurchase_0_10, memo`

`blend_note` は開発指示書のデータ項目には無いが、既存 Excel に実データが入っているため取りこぼさないよう保持している。
`temp` は既存データが `8C` のような単位付き文字列なので、数値化せず文字列のまま持っている。

### color と style

Excel テンプレートのドロップダウンに合わせている。

- `color`: **red / white / roze / orange**
- `style`: **still / sparkling**

開発指示書では color が `red/white/rose/sparkling` と書かれているが、テンプレートでは
**泡は color ではなく style で表す**設計になっているため、そちらに揃えた
（スパークリングロゼなら `color=roze, style=sparkling`）。
綴りが `rose` ではなく `roze` なのもテンプレート由来で、Excel と値をそのまま
行き来させるためにあえて揃えてある。インポート時は `rose` / `ロゼ` / `rosé` も
`roze` に正規化するので、手書きの表記ゆれは吸収される。

color 列に `sparkling` と書かれた行は取り込まずスキップし、
「style 列に入れてください」という案内を画面に出す。

## マスタデータ

コンボボックスの候補は `backend/app/data/masters.json`（31カ国・661地域・108品種）。
既存 Excel テンプレートのドロップダウンリストシートから生成している。
テンプレートを更新したら、以下を流し直せばアプリ側の候補も更新される。

```bash
cd backend && .venv/Scripts/python scripts/build_masters.py "path/to/wine_log.xlsx"
```

シートは名前ではなく中身で判定している（`country` / `region` / `variety` の見出しが揃い、
かつ region の行数が最も多いシートを選ぶ）。記入例シートにも同じ見出しが並んでいて、
名前もファイルによって「ドロップダウンリスト」だったり「Sheet2」だったりするため。

API が返す候補は、このマスタと**DB に既に登録済みの値**を合成したもの。
マスタに無い産地を手入力しても、次回から候補に出る。

## クラスター分析の計算方法

PCA と同じ軸・同じ標準化行列を使う（R 側も「PCAと同じ軸(keep)を使って距離行列を作成」している）。
その下ごしらえを `_prepare()` に切り出して、PCA とクラスタリングの両方から呼んでいる。

クラスタリングは sklearn の `AgglomerativeClustering(linkage="ward")`。
これは R の `hclust(method = "ward.D2")` と同じ定義なので、既存の R の分かれ方と揃う。

グループ番号は**総合評価の平均が高い順**に振り直している。R 側の「★好きクラスタ」に相当する
一群が常にグループ1に来るので、画面で探さなくて済む。

各グループの特徴を表す一言ラベルは、全体平均からのズレが大きい香味軸から自動生成している。
ズレの**向きではなく大きさ**で並べているのが要点で、「樽が平均より0.9低い」ようなグループは
低さこそが特徴なので、正のズレだけを見ると特徴を取り違える。

## ヒートマップの並び順

既定は「評価順」。**行は平均の高い順に上から、列は低い順に左から**並べるので、
評価の良い組合せが表の右上に集まり、対角線状のパターンとして読める（R 版の出力と同じ向き）。
「本数順」に切り替えると、行・列とも記録の多い順になり、どこにデータが溜まっているかを見られる。

行・列の平均は**本数で重み付け**している。単純にセルの平均を平均すると、
1本しかないセルが4本のセルと同じ重みになってしまうため。

既定は「地域 × 2本以上」。品種マスタ108種に対して記録が80件しかないので、
1本だけの組合せまで出すと表がほぼ空白になり、そもそも1本の値は平均と呼べない。

色の濃淡は**表示されているセルの範囲**で正規化する。全記録の最小・最大で固定すると、
絞り込んだときに濃淡がほとんど付かなくなる。濃い側をこれ以上明るくすると
セルの文字とのコントラストが 4.5:1 を割るため、濃淡の幅は淡い側を暗くして稼いでいる。

## 記録の編集

記録一覧の「編集」を押すと、その記録が左の入力フォームに読み込まれる。
フォームは新規入力と同じものを使い回し、保存ボタンが「この記録を更新」に変わる。
「編集をやめる」で新規入力に戻る。

フォームに読み込むとき、数値の未入力は `null` のまま保持している（`toForm()`）。
0 で埋めてしまうと、**評価を付けていない項目が「0点を付けた」に化けて**、
そのまま更新すると PCA の分散スクリーニングや平均値に影響してしまう。
総合評価のスケールも、未評価のときは 0 と区別してドットを1つも点けない。
